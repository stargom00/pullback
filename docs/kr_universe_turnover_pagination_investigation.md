# KR 유니버스 "거래대금 상위" 오염 조사 (2026-09-01)

## 배경

JW신약(067290.KQ)/에이플러스에셋(244920.KS, 최초 조사 시 접미사 착오로
`.KQ`로 확인해 "유니버스에 없다"는 오판이 있었음 — 아래 "알려진 이슈"
절 참고)이 스캐너에 안 잡히는 이유를 조사하던 중, KR 동적 유니버스
(`universe.get_universe("kr")`, ~1500종목)가 이름과 달리 실제로는
"거래대금 상위"가 아니라는 것을 발견했다.

## 발견 1 — `naver_kr.fetch_top_value()`의 페이지네이션이 깨져 있다

`finance.naver.com/sise/sise_quant.naver`(거래대금 순위 페이지)를
`page` 파라미터를 1~59까지 바꿔가며 직접 호출해도 **완전히 동일한
콘텐츠**(코스피 81개/코스닥 96개, 순서까지 동일)가 반환된다(실측
재현, HTTP 200·정상 HTML 135KB — 에러 아님). 원본 HTML엔 페이지 링크
자체가 안 보이고(`page=2` 리터럴 없음), 대신 `nxt_sise_quant.naver`라는
새 링크가 발견됨 — 한국 NXT(대체거래소) 관련 사이트 개편 가능성이
있으나 확정은 아니다. **로컬에 이 함수의 과거 실행 로그가 없어 "언제부터"
인지는 git 이력으로도 확인 불가.**

## 발견 2 — 그 결과 유니버스의 91%가 시가총액 폴백으로 채워진다

`fetch_top_value(1500)`의 내부 단계별 실측:

| 단계 | 종목 수 |
|---|---|
| 거래대금(turnover) 페이지에서 실제 확보(ETF 제외 후) | 133개 (8.9%) |
| 시가총액 폴백에서 신규 추가 | 1,367개 (91.1%) |
| 최종 top_n(1500) 트림 후 | 1,500개 |

`fetch_top_marketcap()`이 쓰는 `sise_market_sum.naver`는 페이지네이션이
**정상 동작**(직접 확인) — 그래서 폴백 경로 자체는 문제없이 작동하고,
결과적으로 "거래대금 상위 1500"이 실질적으로 "시가총액 상위 ~1500"이
되어버렸다.

**영향받는 기능**: 종가베팅(jongga) "base(거래대금 상위100)" 조건 —
`turnover_rank`는 이 왜곡된 유니버스 안에서만 재계산되므로, 시총은
작지만 당일 거래대금이 실제로 큰 종목은 애초에 후보 풀에 없어 걸릴
수가 없다. 상세·조치는 `docs/kr_jongga_betting_backtest.md` 상단 경고
참고.

## 발견 3 — 시총 상위 300 비중은 16.2%, "메가캡 쏠림"은 아님

현재 유니버스 1504개 중 (KOSPI+KOSDAQ 통합) 시가총액 상위 300위 이내:
244개(16.2%). 메가캡이 유니버스를 압도하는 구조는 아니다 — 다만 "오늘
거래대금이 몰린 곳"이 아니라 "평소 시총 순위가 top-1500 안에 드는 곳"
으로 종목 풀이 고정돼 있다는 성격 문제는 그대로다.

## 대안 소스 조사

| 소스 | 인증 | 확인된 제한 | 상태 |
|---|---|---|---|
| **m.stock.naver.com 모바일 API** | 불필요(UA+Referer만) | 미상. `pageSize=100` 정상, `1000`은 거부 | ✅ 채택 — 페이지네이션 정상 작동 확인(page별 실제 다른 종목 반환), 응답에 `accumulatedTradingValue`(당일 누적거래대금) 포함 |
| 다음(Daum) 증권 | 불명 | 미상 | `/api/*` 경로가 403(Referer 없음)→500(Referer 추가 후) 반응 — 엔드포인트 존재 가능성 높으나 정확한 파라미터 미특정. 추가 조사 시 브라우저 개발자도구로 실제 요청 캡처 권장 |
| KIS Developers API | 필요(증권계좌+API 신청) | 공식 문서에 "거래대금순위" API 존재 확인(WebFetch), 정확한 초당/일일 제한 미확인 | 가능하나 진입장벽 있음 |

## 조치 — `fetch_top_turnover_v2()` 신설 (naver_kr.py)

m.stock.naver.com의 `marketValue`(시총순 정렬) 엔드포인트를 전체
시장(KOSPI 2,485종목/KOSDAQ 1,822종목, `pageSize=100`씩 페이징, 총
~44회 요청)에 대해 훑은 뒤, 응답에 이미 포함된 `accumulatedTradingValue`
로 직접 재정렬해 top_n을 뽑는다. **기존 `fetch_top_value()`는 건드리지
않음** — 비교 측정이 끝나기 전엔 운영 경로(`get_universe`/
`load_kr_dynamic`)를 바꾸지 않는다(사용자 지시).

실측(2026-09-01): 실행시간 62.2초, 44회 요청 전부 성공(재시도 없이
0건 실패). 기존 유니버스와 비교(정적 KR_UNIVERSE는 양쪽 동일, 동적
부분만 비교):

| | 종목 수 |
|---|---|
| 겹침 | 1,238 (82.5%) |
| 기존에만 있음(신규엔 빠짐) | 266 — KOSPI 69 / KOSDAQ 197 |
| 신규에만 있음(기존엔 없던 새 종목) | 262 — KOSPI 104 / KOSDAQ 158 |

신규 편입 종목 상위권에 최근 상장주(상장 6~90거래일)가 다수 포함됨 —
시총 순위는 아직 못 올라왔지만 거래대금이 실제로 터진 케이스로, base
조건의 원래 취지("오늘 돈이 몰린 곳")에 정확히 부합. 기존(시총폴백)
유니버스는 이런 종목을 구조적으로 놓칠 수밖에 없었다.

종가베팅 백테스트를 이 신규 유니버스로 재실행한 결과는
`docs/kr_jongga_betting_backtest.md`에 별도 기록.

## 알려진 이슈 (수정 안 함, 기록만) — `naver_kr.to_code()`가 티커 접미사를 검증하지 않는다

이번 조사 중 "에이플러스에셋이 유니버스에 없다"고 잘못 결론 내린 원인.
`to_code()`는 `ticker.split(".")[0]`으로 접미사(.KS/.KQ)를 그냥
잘라내기만 하고 실제로 어느 시장인지는 검증하지 않는다:

```python
def to_code(ticker: str) -> str:
    return ticker.split(".")[0].zfill(6)
```

Naver `siseJson` API 자체가 6자리 코드만 받고 시장 구분을 안 쓰기
때문에(코드가 KOSPI/KOSDAQ 통틀어 유니크), **잘못된 접미사로 조회해도
에러 없이 데이터가 그대로 반환된다.** 실제 사례: 에이플러스에셋의
정확한 티커는 `244920.KS`(코스피, `sosok=0`으로 API 재확인)인데
`244920.KQ`(코스닥)로 `fetch()`/`fetch_history()`를 호출해도 정상적으로
484봉이 반환됨 — "데이터가 나온다"가 "접미사가 맞다"를 보장하지 않는다.

**영향 범위 미조사** — `get_universe()`가 반환하는 dict의 key(정확한
접미사)와 다른 접미사로 티커를 다루는 코드가 이 레포 어딘가에 더
있다면 같은 착오가 조용히 숨어있을 수 있다. 의심되는 티커는
`t in get_universe("kr")`로 정확한 키 존재 여부부터 확인할 것.
수정(예: `to_code()`가 실제 시장과 불일치 시 경고/보정)은 사용자 지시로
보류 — 이 문서와 `CLAUDE.md` "알려진 설계 갭"에 기록만 남긴다.
