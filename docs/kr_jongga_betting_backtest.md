## 배경

"실전 고수 조건"(당일 강한 양봉 + 거래량 폭발 + 유동성 상위 + 이평선
위 + 신고가 근접)을 계량 조건으로 번역해, T일 종가 매수 → T+1일 시가
매도(종가베팅) 전략이 새 탭으로 신설할 만한 엣지가 있는지 사전 등록
백테스트로 검증한다.

## 전략 정의

- **기본 시나리오**: T일 종가 매수 → T+1일 시가 매도.
- **보조 시나리오**: T+1일 고가 매도 — 단, 이 레포가 가진 건 일봉
  (daily OHLC)뿐이라 "오전 고가"가 아니라 **T+1 하루 전체의 고가**로
  근사했다(장중 타임스탬프 데이터 없음 — 한계로 명시, 실제 오전 매도가
  이보다 낮을 수 있어 참고용 상한치로만 본다).

## 후보 조건

| 조건 | 정의 |
|---|---|
| base | 당일(T) 거래대금(종가×거래량) KR 전종목 상위 100 이내 |

| theme | **측정 불가로 제외** — 아래 "theme 조건 제외 사유" 참고 |

## 방법론

- **체크포인트**: `checkpoints(60,250,10)` 20개 — 세션 전체 공용 표준.
- **데이터**: harness 기본 KR fetch(730일, ≈490거래일)는 off=250 +

  직접 fetch — harness.py는 확장 안 함(이 백테스트 전용 요구사항).
- **비용**: 왕복 수수료+슬리피지 0.3%(사용자 지시) 차감 후 수익률을
  "비용차감후"로 표시.
- **z검정**: `harness.ev_gap_zscore`는 -1/0/+2R 이산분포 전용 공식
  (README 규칙7)이라 이 연속형 % 수익률엔 안 맞아, 표준 2표본 평균차
  z검정(표본분산 기반)을 이 스크립트에 새로 작성 — 재구현이 아니라
  애초에 다른 데이터 타입에 맞는 통상 공식.
- **규칙6**(대조군 유동성매칭): 대조군 자체가 base(거래대금 상위100)라
  그대로 충족.
- **규칙8**(KR/US 미혼합): KR 단일 시장만 다뤄 해당 없음.

근거 스크립트: `scripts/measurements/2026-08-29_kr_jongga_betting_backtest.py`.

### 대조군(base) 대비 유의성

base 평균갭 +0.49%(n=1,884) vs 최종조합 평균갭 +1.94%(n=70) — 격차
**+1.45%p, z=1.84**. 사전 기준(z≥1.96)에 **살짝 못 미친다**(양측 95%

(최종조합 n=70) 검정력 자체가 낮다는 점이 큰 원인 — 효과 크기(+1.45%p)
자체는 base 평균의 3배에 가까운 큰 폭이다.

## 판정 — 사전 기준 미달(경계선), 보류

**(a) 충족(+1.64% ≥ +0.5%), (b) 충족(두 절반 다 재현), (c) 미달
(z=1.84 < 1.96) — 셋 다 충족을 요구한 사전 기준상 최종 판정은
"조건 재설계 또는 보류".** 세 기준 중 하나가 근소하게 미달이라고
바로 확대해석해 채택하지 않는다 — 사전 등록의 취지 자체가 사후에
기준을 낮춰 끼워맞추는 걸 막는 것.

다만 완전한 무신호와는 다르다: 효과 크기가 크고(base 대비 +1.45%p,
약 3배) 시간 반분도 재현됐다 — z=1.84는 "우연과 완전히 구분 안 됨"
(has_maejip z=1.94와 마찬가지로 절대 기각권이 아니라 표본 부족형
미달)에 가깝다. **다음 단계 후보**: 조건을 유지한 채 표본을 늘려
재현 확인(다른 실행일/체크포인트 밀도 확대) — has_maejip 사례에서
표본을 늘려 재검증했던 것과 동일한 절차. 이번 라운드에서는 탭 신설
보류, scanner.py/app.py/static 미변경.

다를 수 있다는 흔한 패턴 — 개별 항목의 단독 방향만으로 조합에서의
역할을 예단하면 안 된다는 교훈).

## 운영 반영 완료(2026-09-02) — 부분 교체(전면 교체 아님)

이전 절에서 검토했던 "종가베팅 탭에만 한정해 v2 유니버스를 별도로
적용"하는 부분 교체안을 그대로 구현했다(사용자 지시). **`get_universe
("kr")`(전 탭 공유 스캔 대상 유니버스)는 손대지 않았다** — 아래
"다른 탭에 미치는 영향" 절의 우려(RS 순위 이동, 신규/이탈 종목의
다른 탭 히트 변화)가 이번 변경으론 발생하지 않는다.

**구현 내용** (`app.py`):
- `_run_scan_jongga()`의 `turnover_rank` 계산부만 분기: 환경변수
  `JONGGA_TURNOVER_SOURCE`(기본 `"v2"`)가 `"v2"`면
  `naver_kr.fetch_top_turnover_v2()`로 만든 진짜 거래대금 순위를
  `kr_data`(= `get_universe("kr")` 기반, 안 바뀜)의 종목에만 매핑한다.
  `"v1"`이면(또는 v2가 실패/incomplete면) 기존 로직(`kr_data` 내부
  close×volume 재계산, `get_universe` 유니버스 안에서만 상대순위)을
  그대로 쓴다. v2가 top_n(1500) 밖이라 순위가 없는 종목은 `None`으로
  남아 `analyze_jongga()`의 base 조건(상위100)을 자연히 통과 못 한다.
- **롤백 스위치**: `JONGGA_TURNOVER_SOURCE=v1` 환경변수만 Railway에서
  바꾸면 코드 배포 없이 즉시 구 로직으로 복귀(v5.139 돈의흐름
  킬스위치와 같은 패턴).
- **44회 요청 실패 처리**: `_load_jongga_turnover_v2_rank()`가
  `fetch_top_turnover_v2()`의 `stats.incomplete=True`(연속 2회 페이지
  실패로 한 시장이라도 못 끝까지 훑음)를 감지하면 **그 결과를 캐시에
  저장하지 않고** `None`을 반환해 그 호출은 v1으로 폴백한다 — 부분
  유니버스가 조용히 캐시로 굳어지는 일이 없다. fetch 자체가 예외를
  던지거나 결과가 비어있는 경우도 각각 로그를 남기고 v1으로 폴백
  (`except: pass` 없음 — 모든 실패 경로가 `print()`로 원인을 남김).
- **캐시**: 파일명 `kr_turnover_v7_jongga_{YYYY-MM-DD}.json`
  (`_resolve_persistent_path()` — JOURNAL_DIR→/data→앱폴더 우선순위,
  universe.py의 `kr_universe_v6_*.json`과 이름이 겹치지 않아 신구
  캐시가 섞일 위험 없음). **갱신 시점**: 하루 1회 — 그날 첫 종가베팅
  스캔 시도 시 캐시가 없으면 그 호출이 62초 콜드스타트를 감수하고
  fetch+저장하고, 이후 같은 날 호출은 전부 캐시 히트(즉시 반환).
  종가베팅은 하루 1회(14:40~15:00 자동 스냅샷) + 가끔 수동 재실행
  정도만 호출되므로 하루 여러 번 62초가 반복될 실질적 위험은 낮다.
  incomplete여서 캐시가 안 만들어진 날은 그날의 다음 호출이 다시
  fetch를 시도한다(같은 날 재시도 스톰 위험은 호출 빈도가 낮아 낮음).
- **표기 갱신**: `JONGGA_BACKTEST_NOTE`를 신규 수치(+0.80%, n=292,
  z=3.54, v2 유니버스)로 갱신, "⚠️ 운영 미반영" 문구 제거(구 수치는
  "원측정"으로 병기 유지). `GUIDE.md` 6.5장의 "2026-09-01 현재
  미반영" 캐비어트를 "당일 거래대금 상위 100(전종목 기준, v2
  유니버스)"로 확정.

**검증 방법(배포 후)**:
1. `GET /api/scan?market=kr&mode=jongga`(또는 종가베팅 탭 새로고침)
   응답의 `diag.turnover_rank_source`가 `"v2"`인지 확인 — v1 폴백이
   조용히 일어났는지 여기서 바로 구분된다.
2. Railway 환경변수에 `JONGGA_TURNOVER_SOURCE=v1`을 임시로 설정하고
   재배포 없이(환경변수 변경만으로 재시작됨) 같은 스캔을 다시 호출 —
   `diag.turnover_rank_source`가 `"v1"`로 바뀌고, `hits` 목록(종목·
   turnover_rank)이 v2 때와 달라지는지 비교한다. 유니버스 17.5%가
   교체된 재측정 결과(비용차감후 +1.22%→+0.80%)를 감안하면 실제
   서비스에서도 v1/v2 후보 목록에 눈에 띄는 차이가 나는 게 정상이다
   — 완전히 동일하게 나오면 오히려 v2 경로가 실제로 안 타고 있다는
   신호이니 재점검. 확인 후 환경변수를 다시 `v2`(또는 삭제, 기본값이
   v2)로 되돌린다.
3. 캐시 파일(`kr_turnover_v7_jongga_{오늘날짜}.json`, `/data` 볼륨)의
   `stats.incomplete`/`kospi_fetched`/`kosdaq_fetched` 필드로 그날
   fetch가 완전했는지 직접 확인 가능.

**다른 탭에 미치는 영향 — 이번 변경으로는 없음(위 "부분 교체" 설계
그대로 구현됐기 때문)**. 아래는 향후 `get_universe("kr")` 자체를
전면 교체할 경우를 대비해 남겨두는 참고 기록이다:
- `get_universe("kr")`는 돌파/박스돌파/추세전환/돌파임박/눌림목 등
  **전 탭이 공유**한다. 종가베팅만 새 유니버스로 재측정했고 **다른
  탭들은 v2 유니버스로 재측정된 적이 없다** — 전면 교체하면 이
  탭들의 스캔 결과(히트 수·랭킹)도 같이 바뀐다.
- 시총폴백으로만 들어와 있던 266개 종목이 유니버스에서 빠지면, 그
  종목들이 다른 탭에서 잡던 히트도 같이 사라진다.
- 신규로 들어오는 262개 종목(최근 상장주 다수 포함)이 다른 탭에서
  새로 히트가 될 수 있다 — 이 중 상당수는 다른 탭들의 `min_bars`
  요구치(150~260봉)를 못 채워 실제로는 걸러질 가능성이 높지만 확인 안
  됨.
- RS 랭킹(`rs_ranks`/`rs_moms`)은 유니버스 구성원 전체를 상대평가하므로,
  유니버스가 바뀌면 **안 바뀐 종목들의 RS 순위도 같이 이동**한다(모집단이
  바뀌니 상대적 위치가 바뀜) — 이건 종가베팅과 무관한 탭들에도 영향.
  전면 교체는 별도 지시 없이는 진행하지 않는다.
