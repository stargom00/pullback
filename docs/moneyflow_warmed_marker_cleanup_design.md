# `moneyflow_warmed_*.marker` 정리 설계 (2026-09-02, 사용자 지시)

설계만 — 코드 미작성. **구현 시점엔 `app.py` 수정이 필요한데, 지금 다른 세션이
`app.py`(종가베팅 base조건 캐비어트, VERSION→v5.144)를 작업 중이라 그 작업이
커밋된 뒤 리베이스해서 진행할 것.** 이 문서 자체는 `app.py`와 무관한 새 파일이라
지금 써도 충돌 없음.

## 배경

v5.140에서 도입한 `moneyflow_warmed_{market}_{daykey}.marker` 파일이 거래일마다
하나씩(KR·US 각각) `/data`에 쌓인다. v5.141 이후 이 마커의 실제 역할이 좁혀졌다는
점이 이 설계의 전제: 유료 API 재호출 방지(비용 안전)는 이제
`money_flow_report.py` 자신의 `last_success_daykey` 게이트가 전담하고, 이
`app.py` 레벨 마커는 **"1단계 무료 계산(`money_flow.run_daily`)을 4분 스케줄러
틱마다 반복하지 않기 위한" 순수 효율화 장치**로 재정의됐다(v5.143 커밋 메시지
참고). 즉 오늘 날짜 마커 1개만 기능적으로 의미 있고, 그보다 오래된 마커는
게이트 판정에 전혀 관여하지 않는다 — 순수 디버깅/이력 조회용으로만 남는다.

## 1. 보존 기간 — 7일 제안

**기능적 필요치는 0일(오늘 것만)**: `_mark_moneyflow_warmed()`는 항상 "오늘
daykey" 하나만 조회한다. 어제 이전 마커는 게이트 로직이 절대 안 읽는다.

**디버깅 가치 관점에서 7일을 제안하는 근거**:
- 이 저장소에 이미 있는 "1주일" 관례를 그대로 재사용 — `macro_calendar.py`의
  `_MACRO_CALENDAR_STALE_DAYS = 7`과 동일 기준. 새 숫자를 발명하지 않음.
- 실전 디버깅 시나리오는 "어제/그제 스케줄러가 정상 실행됐는지" 확인 정도가
  대부분이고, 그보다 오래된 건 마커(빈 파일, 생성 여부만 표시)보다
  `money_flow.json`(1단계 스냅샷 원본, 내용이 풍부함)이나 서버 print 로그가
  더 유용한 소스라 마커 자체의 장기 보존 가치는 낮다.
- 디스크 비용은 애초에 무시 가능한 수준(마커 1개=0바이트, 연간 KR+US 합쳐
  약 500개=수백 KB 이하 inode 오버헤드뿐)이라 "용량 절약"이 아니라 "`/data`
  디렉터리 목록이 안 지저분하게" 유지하는 게 이 정리의 실제 목적 — 그 목적엔
  7일이면 충분.
- 대안: 3일(더 타이트, "그저께까지"만) 또는 30일(theme_map의 `STALE_DAYS`와
  통일). 어느 쪽이든 디스크 비용 차이는 없으므로 순수 "얼마나 되돌아볼 일이
  있는가"의 판단 — 7일을 기본값으로 제안하되 사용자가 다른 값을 원하면
  상수 하나만 바꾸면 됨(로직에 영향 없음).

## 2. 정리 시점 — 마커 생성 시 함께(기존 코드베이스 관례 재사용)

이 저장소에 이미 정확히 같은 문제·같은 해법의 선례가 있다 —
`_save_disk_cache()`(`app.py:4426` 부근)가 새 캐시 파일을 저장하는 시점에
같은 market의 오래된 캐시를 즉시 지운다. 마커도 동일 패턴을 그대로 재사용:

**주 트리거: `_mark_moneyflow_warmed()`가 새 마커를 실제로 "새로 생성"했을 때만**
(반환값 `True`인 경우 — 이미 있던 마커라 `FileExistsError`로 `False`를 반환한
경우는 정리를 또 돌릴 필요 없음, 오늘 마커는 어차피 안 지워지므로) 같은
디렉터리를 스캔해서 보존기간을 넘긴 마커를 지운다.

- **왜 스케줄 잡을 새로 안 만드나**: 이 저장소는 4분 스케줄러 루프
  (`_scheduler_loop`)가 있지만, 거기에 정리를 얹으면 "정리용 상태"(마지막 정리
  날짜)를 또 하나 영속화해야 하고, 그 상태 파일 자체가 이번 사고와 같은 유형의
  실수(메모리/파일 동기화 어긋남)를 만들 여지가 생긴다. 마커 생성 자체가
  "새 거래일이 시작됐다"는 이벤트이므로, 그 이벤트에 얹는 게 별도 상태 없이
  정확히 하루 한 번(시장당) 자연스럽게 도는 방법.
- **왜 앱 시작 시(`@app.on_event("startup")`)를 주 트리거로 안 쓰나**: 이번
  사고의 원인 후보였던 "컨테이너가 잦게 재시작"이 사실이라면, 시작 시점 트리거는
  그 재시작 빈도만큼 자주(예: 19분마다) 도는 셈이라 트리거 빈도가 인프라 상태에
  종속된다 — 정리 자체는 가벼운 파일 스캔이라 자주 돌아도 실질적 해는 없지만,
  "언제 도는가"가 예측 불가능해지는 게 깔끔하지 않음.
- **보조 트리거(선택, 권장)**: 그래도 앱 시작 시 같은 정리 스윕을 한 번 더
  걸어두는 걸 2차 안전망으로 제안 — 킬스위치가 오래 꺼져있어 새 마커가 한동안
  안 생기는 기간(주 트리거가 안 도는 기간)에도 디렉터리가 무한정 안 불어나게.
  비용은 `os.listdir` 1회 스캔뿐이라 재시작이 잦아도 무해.

## 3. 삭제 실패·권한 문제 시 동작 — 완전 best-effort, 게이트 성공을 절대 방해 안 함

`_save_disk_cache()`의 기존 관례를 그대로 따름 + 가시성 한 줄 추가:

- 정리 로직 전체를 `_mark_moneyflow_warmed()`가 마커 생성에 **성공한 뒤**
  실행하고, 정리 자체는 `try/except OSError`로 감싸 실패해도 함수의 반환값
  (`True`/이번 호출이 실행 담당)에는 전혀 영향을 주지 않는다 — 정리가 뭘 하든
  이 호출은 이미 오늘 마커를 만드는 데 성공했으므로 스케줄러는 정상 진행해야
  함(정리 실패로 리포트 생성 자체가 막히면 안 됨 — 본말전도).
- 개별 파일 삭제도 파일 단위로 각각 `try/except OSError: pass`(단, 여기선 기존
  `_save_disk_cache`와 달리 `print()` 한 줄을 추가해 가시성 확보 — 이번 사고
  교훈("사람이 로그를 따로 읽어야만 작동하는 장치"가 아니라, 실패해도 최소한
  로그는 남겨서 나중에 추적 가능하게). 디렉터리 스캔(`os.listdir`) 자체가
  실패하는 경우(권한 문제 등)도 같은 방식 — 이번 정리 사이클을 건너뛰고
  다음(다음 거래일의 새 마커 생성 시)에 다시 시도, 별도 재시도 로직 불필요
  (스스로 다음 자연 트리거 때 재시도됨).
- 파일명 매칭은 정규식으로 엄격하게(`moneyflow_warmed_(kr|us)_\d{4}-\d{2}-\d{2}\.marker`)
  제한해서, 패턴이 안 맞는 파일(예: 향후 다른 목적의 파일이 우연히 비슷한
  이름을 가진 경우)은 절대 안 건드림 — `_save_disk_cache`가 `datacache_`
  접두사+파츠 개수를 검증하는 것과 같은 방어.
- 날짜 판정은 **파일의 mtime이 아니라 파일명에 박힌 daykey 문자열을 파싱**해서
  계산(`오늘(KST) - daykey`). 마운트/백업 등으로 mtime이 실제 생성 시각과
  달라질 수 있는 영속 볼륨 환경에 더 안전 — 마커 자체가 daykey를 이름에
  그대로 담고 있어 별도 메타데이터 없이도 결정론적으로 계산 가능.

## 4. 다른 영속 파일도 같은 문제가 있는가 — 확인 결과: 없음(설계상 이미 안전)

v5.141에서 새로 만든 세 상태 파일을 코드 기준으로 다시 확인:

| 파일 | 키 구조 | 갱신 방식 | 날짜별 누적? |
|---|---|---|---|
| `money_flow_report_state.json` | `{"kr": {...}, "us": {...}}` — 시장 2개 고정 키 | 매번 **같은 키를 덮어쓰기**(`m["last_success_daykey"] = daykey`, `m["last_attempt_ts"] = now_ts`) | **아니오** — 시장당 스칼라 필드 2개뿐, 크기가 시간과 무관하게 고정 |
| `api_call_guard_state.json` | `{"date", "count", "warned", "blocked_notified", "pending_alert"}` 단일 dict | 오늘 날짜가 바뀌면 `_load()`가 통째로 새 dict로 교체(과거 데이터 유지 안 함) | **아니오** — 하루치 상태만 존재, 자체적으로 매일 리셋 |
| `macro_calendar_guard_state.json` | `{"last_attempt_ts"}` 단일 dict | 매번 덮어쓰기 | **아니오** |

**결론: 위 세 파일은 이미 설계상 정리가 필요 없다** — 전부 "하루치/시장별
고정 필드를 덮어쓰는" 구조라 며칠이 지나든 파일 크기가 늘지 않는다. 이번
사고(v5.140 마커)가 문제였던 이유는 정확히 "daykey를 파일명/키에 넣어서
**새 파일을 매번 추가**"하는 구조였기 때문 — 위 세 파일은 처음부터 그 함정을
피해서 설계했다(같은 market/date 키를 계속 덮어씀).

참고로 범위 밖이지만: `theme_map.json`은 테마명을 키로 쓰고 재생성 시 같은
키를 덮어쓰므로(날짜가 아니라 테마명이 키) 날짜별 누적 문제는 없음 — 다만
테마 종류 자체가 무한정 늘어나면(현재는 소수의 고정된 KR 섹터/테마 명 위주라
실질적 위험 낮음) 이론적으로는 커질 수 있음, 이번 조사 범위 밖이라 별도 확인
필요시 요청 바람.
