# 저널 저장 구조 — 탭 간 덮어쓰기 경쟁 설계 검토 (2026-09-02, 설계만·구현 안 함)

## 배경 — 확인된 구조

`static/index.html`:
- `journalCache`(전역 JS 변수)는 탭이 열릴 때 `loadJournalFromServer()`로
  **딱 한 번** 서버에서 로드된 뒤, 그 탭이 살아있는 동안 메모리에 그대로
  남는다. 이후 서버의 실제 변경 사항을 자동으로 다시 읽어오지 않는다.
- `setJournal(arr)`이 **유일한 저장 진입점**(19곳에서 호출 —
  `saveJournal`/`markEntered`/`markMissed`/`revertToPending`/`reopenRow`/
  `markWatchEntered`/`markWatchMissed`/`markWatchClosed`/`reopenWatch`/
  `cleanupExpiredWatches`/`savePartial`/`saveEdit`/`updateResult`/
  `delJournal`/`saveManualAdd`/전체삭제 버튼, 그리고 **자동 실행되는**
  `updateTracking`/`checkLeaderConversions`). `_journalSaveChain`으로
  같은 탭 안의 저장 호출끼리는 직렬화하지만(v5.102, 순서 보장), **다른
  탭이 들고 있는 스냅샷과는 무관** — 탭 간 조율 장치가 전혀 없다.
- `POST /api/journal`(서버, `save_journal()`)은 받은 배열을 **버전 비교
  없이 그대로 통째로 덮어쓴다**(`.bak` 백업은 뜨지만 "직전 파일" 백업일
  뿐 충돌 감지가 아니다).
- 참고: `updateTracking()`/`checkLeaderConversions()`는 실제로 상태가
  바뀐 게 있을 때만(`changed === true`) 저장을 호출한다 — 매 폴링마다
  무조건 쏘는 건 아니지만, **사용자 조작 없이도** 저장이 트리거될 수
  있다는 점은 그대로다(예: 가격이 손절가를 건드려 자동 종료 처리되는
  순간).

## 위험 시나리오 (사용자 지시 원문)

1. 탭 A, 탭 B를 동시에 연다 — 둘 다 시점 T의 저널(N건)을 `journalCache`에
   가짐.
2. 탭 A에서 새 기록을 추가 → 서버 파일이 N+1건이 됨.
3. 탭 B는 이 변경을 모른 채(자기 메모리는 여전히 N건), 나중에 아무
   이유로든(수동 조작 또는 `updateTracking`의 자동 종료 판정) 저장이
   트리거됨 → 탭 B의 스냅샷(N건, A의 추가분 없음)을 그대로 POST →
   서버 파일이 다시 N건으로 되돌아가며 **A가 추가한 기록이 조용히
   사라진다.**

## 대안 3가지 — 작업량·위험도 비교

### 대안 1 — 레코드 단위 API 분리 (전체 덮어쓰기 폐지)

**설계**: `POST /api/journal`(전체 배열)을 없애고 `POST /api/journal/add`
(1건 추가) / `PATCH /api/journal/{id}`(1건 필드 수정) /
`DELETE /api/journal/{id}`(1건 삭제)로 쪼갠다. 서버는 매 요청마다
`load_journal()`로 새로 읽어 **그 레코드 하나만** 고치고 다시 쓴다 —
이미 이 레포의 다른 저장소(`_load_reignition_watch`/`theme_map._load`,
2026-09-02 조사에서 "매번 새로 읽고 그 자리에서 씀"이 안전 패턴임을
확인)와 같은 방식이라 구조적으로 이 레이스가 성립하지 않는다(다른
탭의 변경을 "몰라서 지우는" 게 아니라 애초에 자기가 아는 부분만
건드리므로).

- **남는 위험**: 두 탭이 **같은 레코드**를 동시에 고치는 경우만 좁은
  범위로 남는다(예: 둘 다 같은 트레이드를 "종료" 처리) — 이건 대안 2의
  버전 체크를 레코드 단위로 얹으면 마저 막을 수 있음(둘을 배타적으로
  볼 필요 없음, 병행 채택 가능).
- **작업량**: **큼.** 19개 호출부 전부가 지금 "배열 전체를 통째로
  받아 필드 하나 고치고 setJournal(j)"인 패턴이라, 각 호출부를 "이
  레코드의 이 필드만 PATCH"로 하나하나 다시 짜야 한다 — 서버 쪽 신규
  엔드포인트 4~5개 + 클라이언트 19곳 리팩터 + 상태 전이(pending→entered
  등)마다 회귀 테스트 필요. 개인 어림잡아 1~2일 규모.
- **위험도**: 중간~높음(작업량이 큰 만큼 마이그레이션 중 특정 호출부
  하나를 놓치는 실수 가능성). 다만 구조 자체는 **가장 근본적으로
  깨끗한 해법** — "언젠가"로는 가장 유력.

### 대안 2 — 서버측 버전 필드로 충돌 감지 후 거부 (권장, 선행)

**설계**: 저널 파일에 버전 번호를 하나 추가한다(예: 파일을
`{"version": N, "records": [...]}` 형태로 감싸거나, 별도 메타 필드).
`GET /api/journal`이 이 버전을 같이 내려주고, 클라이언트는 그 버전을
기억해뒀다가 `POST /api/journal` 보낼 때 같이 보낸다. 서버는 "지금
파일의 버전"과 "클라이언트가 보낸 버전"이 다르면 **덮어쓰지 않고
409로 거부**한다 — 그 사이 다른 탭이 저장했다는 뜻이므로.

- **클라이언트 처리는 거의 공짜다** — `_saveJournalToServer`가 이미
  `if (!res.ok) throw new Error(...)`로 실패를 잡아 `showSaveError()`
  (기존 "⚠️ 저장 실패" 배너)를 띄우는 경로가 있다. 409도 이 경로를
  그대로 타게 두면(문구만 "다른 탭에서 방금 저장했어요 — 새로고침 후
  다시 시도하세요"로 구분) **새 UI를 거의 안 만들어도 된다.** 자동
  재시도(1회, 800ms 후)는 같은 스냅샷으로 다시 시도하니 어차피 또
  실패하지만, 해가 되진 않는다(약간의 지연만 추가).
  - **트레이드오프**: 이 방식은 "덮어쓰기를 막을 뿐, 사라질 뻔한 A의
    변경을 자동으로 병합해주진 않는다" — 대신 B의 그 시점 변경이
    유실될 위험을 "조용한 데이터 손실"에서 "눈에 보이는 저장 실패 +
    사용자가 새로고침 후 재조작"으로 바꾼다. 개인용 앱에서는 이 정도로
    충분하다고 판단(자동 병합은 배열 diff가 필요해 대안 1급 복잡도로
    되돌아감).
- **구버전 파일 호환**: 기존 파일은 순수 배열이라, 로드 시 배열이면
  `version=0`으로 간주하고 감싸는 마이그레이션 1줄이 필요.
- **작업량**: **작음.** 서버: 파일 포맷에 버전 필드 추가 + 저장 시
  비교 1줄(약 30분~1시간). 클라이언트: 버전 값 들고 있다가 요청에
  실어 보내는 부분만 추가(약 1~2시간, 기존 에러 UI 재사용). 합쳐서
  **반나절 이내**로 추정.
- **위험도**: 낮음~중간. 유일한 리스크는 "409를 빠뜨리고 처리 안 하는
  호출부가 있으면 그 액션만 조용히 실패"인데, 이미 `showSaveError()`가
  공통 경로라 빠뜨릴 여지가 적다.

### 대안 3 — 탭 간 동기화/알림 (BroadcastChannel)

**설계**: 탭이 저장에 성공하면 `BroadcastChannel`(또는 구형 호환이
필요하면 `localStorage` + `storage` 이벤트)로 다른 탭들에 "저널
바뀜"을 방송한다. 받은 탭은 (a) 조용히 `journalCache`를 다시 로드하거나
(b) "다른 탭에서 저널이 바뀌었어요 — 새로고침" 배너만 띄운다.

- **이것만으로는 레이스를 막지 못한다** — 사용자가 배너를 못 보고
  넘어가거나, `updateTracking`이 배너 확인 전에 자동으로 먼저 저장을
  쏘면 그대로 재현된다. **경고/완화 장치이지 구조적 해결책이 아니다.**
- **대안 2와 결합하면 시너지가 있다**: 방송을 받은 탭이 자동으로
  최신 버전을 다시 받아두면, 대안 2의 409가 실제로 뜨는 빈도 자체가
  줄어든다(항상 최신 버전을 들고 있게 되므로) — 즉 3은 2의 정확성을
  해치지 않으면서 "409를 얼마나 자주 만나는가"만 줄여주는 UX 보강.
- **작업량**: 작음~중간(`BroadcastChannel` 생성, 저장 성공 시 postMessage,
  리스너에서 배너 또는 재로드 — 약 1~2시간).
- **위험도**: 낮음(실패해도 최악의 경우 알림이 안 뜨는 것뿐, 기존
  동작보다 나빠지지 않음).

## 권장 — 단계적 적용

| 단계 | 내용 | 작업량 | 목적 |
|---|---|---|---|
| 1 (선행 권장) | 대안 2 — 버전 충돌 시 거부 | 반나절 이내 | **조용한 데이터 손실을 눈에 보이는 실패로 전환** — 가장 시급한 위험 제거 |
| 2 (선택, 1 이후) | 대안 3 — 탭간 알림/자동 재동기화 | 1~2시간 | 1번의 409 발생 빈도를 줄여 사용 경험 개선 |
| 3 (언젠가, 규모 큼) | 대안 1 — 레코드 단위 API | 1~2일 | 근본적으로 가장 깨끗한 구조. 1·2 적용 후에도 충돌이 실무적으로 자주 걸리면 그때 착수 |

개인 전용 앱이라 진짜 "동시 편집"은 드물고, 실제로 문제가 되는 경로는
"탭을 여러 개 켜두고 잊어버린 사이 자동 폴링이 조용히 되돌리는" 쪽이라
— **대안 2만으로도 가장 심각한 피해(무손 손실)를 막을 수 있고 비용도
가장 작다.** 대안 1은 구조적으로 우월하지만 지금 문제의 실제 빈도 대비
과한 투자로 판단, "언젠가" 후보로 남긴다.

## 이번엔 구현하지 않음

이 문서는 설계 기록만이다 — 사용자 지시대로 코드 변경 없음. 착수
결정이 나면 대안 2부터 시작하는 걸 제안한다.
