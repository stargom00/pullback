# `/data` 볼륨 정리 — 조사 기록 + 설계 초안 (2026-09-02, 설계만·구현 안 함)

> **우선순위: 낮음(사용자 확인).** Railway 볼륨 5GB 중 현재 122MB(2.4%)
> 사용, 유니버스 캐시 파일 증가율(하루 약 0.6MB, 14개×~45KB)만으로도
> 가득 차기까지 20년 이상 — **긴급하지 않다.** 이 문서는 "언젠가 할 일"
> 수준의 조사·설계 기록이며, 구현은 하지 않았다.

## 1. `kr_universe_v6_1500_*.json` — 하루 14개씩 쌓이는 이유

**원인**: `universe.py`의 `_kr_cache_slot()`(장중 유니버스 캐시 무효화
전략)이 KR 장중(평일 09:00~15:30 KST)엔 **30분 슬롯**으로, 장 외엔
**하루 1회("eod")**로 캐시 키를 나눈다.

```python
INTRADAY_REFRESH_MIN = 30
is_market = (wd < 5) and (9*60 <= minutes <= 15*60+30)
if not is_market: return f"{daykey}_eod"
slot = (minutes // 30) * 30
return f"{daykey}_{slot:04d}"
```

**접미사 의미**: `slot`은 "자정부터 몇 분 지났는지"를 4자리로 채운 값이지
시:분(HHMM) 표기가 아니다. 09:00=540분→`0540`, 09:30=570분→`0570`,
13:00=780분→`0780`, 14:30=870분→`0870`처럼 30분 단위로 증가한다.
09:00(540)부터 15:30(930)까지 30분 간격 슬롯 수 = `(930-540)/30+1 = 14개`,
장 외 "eod" 1개까지 더하면 거래일당 최대 15개 파일이 생길 수 있다 —
사용자가 관찰한 "하루 14개"와 일치.

**보관 필요성 확인 — 전부 불필요, 오늘 것 하나만 유효**:
- `load_kr_dynamic()`은 항상 **오늘·현재 슬롯**의 캐시 키만 조회한다.
  지난 슬롯·지난 날짜 파일을 다시 읽는 코드 경로가 없다 — 새 슬롯에
  진입하면 예전 파일은 그 순간부터 완전히 무의미해진다.
- **정리(삭제) 로직이 아예 없다** — `universe.py` 전체에서 이 파일들에
  대한 `os.remove`/정리 코드를 검색해도 안 나온다. 쓰기만 있고 지우는
  코드가 없는 순수 누적형 구조.

**백테스트가 과거 유니버스 파일을 참조하는지 — 확인 결과: 안 함**.
`scripts/` 전체에서 `kr_universe_v6` 문자열을 검색해도 참조가 0건이다.
모든 백테스트/측정 스크립트는 `universe.get_universe("kr")`을
**실행 시점 기준으로 라이브 호출**한다(그 시점의 "현재" 유니버스를
과거 가격 데이터에 소급 적용하는 방식 — 이 레포 하네스 방법론의 기존
한계이자 전제, 새로운 문제 아님). 즉 **오늘 것 하나를 뺀 나머지 전부는
안전하게 지울 수 있다.**

## 2. `datacache_*.pkl` — 6월 파일이 남아있는 이유

**정리 로직 자체는 존재한다** (`app.py` `_save_disk_cache()`,
`_CACHE_NS`="rs6" 네임스페이스 기준):

```python
def _save_disk_cache(market, daykey, bundle):
    ...
    pickle.dump(bundle, f); os.replace(tmp, path)
    for fn in os.listdir(d):
        if not (fn.startswith("datacache_") and fn.endswith(".pkl")): continue
        fn_ns, fn_market = fn.split("_")[1], fn.split("_")[2]
        if fn_market != market: continue
        keep = fn_ns == _CACHE_NS and fn.endswith(f"_{daykey}.pkl")
        if not keep: os.remove(...)
```

날짜 판정이 파일명 끝(`_{daykey}.pkl`)만 보므로, 파일명 중간에 들어가는
`_universe_sig(market)`(유니버스 종목 수 서명, 예: `u1503`)가 실행마다
달라져도 **삭제 여부와는 무관**하다 — 즉 이 로직 자체는 설계상 맞다.

**그런데도 6월 파일이 남아있는 이유 — 두 가지 후보, 로컬에서 확정 불가**:

1. **정리는 `_save_disk_cache()`가 실제로 "새로 저장"할 때만 돈다.**
   `_fetch_market_data_inner()`를 보면, 오늘 날짜(`daykey`)의 디스크
   캐시가 이미 있으면 `_load_disk_cache()`로 그냥 읽고 **바로
   반환**한다(app.py:4626 부근) — 이 경로는 `_save_disk_cache()`를
   전혀 호출하지 않는다. 즉 **하루에 정말 처음 한 번, 그날 캐시가
   아직 없을 때만** 정리가 실행된다. Railway 배포가 잦으면(이 세션만
   봐도 하루 여러 번 배포) 컨테이너가 자주 바뀌지만, 그것과 무관하게
   "그날의 첫 콜드 캐시 미스"는 하루 1회만 일어나는 게 정상이라 —
   이 자체는 원래 설계 의도대로다. 다만 **어떤 이유로든 그 "하루
   1회"가 특정 날 한 번도 안 걸리면**(예: 그날 앱이 실행되는 동안
   `_warm_market()`의 스케줄러 워밍이 시장별로 계속 디스크 캐시
   히트만 내고, 진짜 콜드 fetch가 트리거될 상황 자체가 안 생기는 경우)
   그날은 정리가 아예 안 돈다 — 다음날, 그다음날도 우연히 안 걸리면
   누적된다.
2. **`except Exception: pass`가 정리 실패를 완전히 숨긴다.** `pickle.dump`
   부터 정리 루프까지 전부 하나의 `try/except Exception: pass`로
   감싸여 있어서(app.py:4473~4502), 정리 루프 중간에 뭔가 실패해도
   (예: 특정 파일 `os.remove` 권한 문제, `os.listdir` 일시 실패)
   **조용히 통째로 무시된다** — 저장 자체는 성공했는지, 정리가 부분
   실행됐는지, 전혀 안 됐는지 로그로 구분이 안 된다. 이 프로젝트
   원칙("발견한 문제는 경고가 아니라 실패로 만든다")에 어긋나는
   지점이라 향후 수정 대상.

**실제 운영 로그(Railway) 없이는 위 둘 중 무엇이 실제 원인인지 확정
못 한다** — 로컬 환경엔 이 함수가 실행된 이력이 없다.

## 3. 볼륨 용량 — 확인됨, 긴급하지 않음

사용자 확인: **Railway 볼륨 5GB, 현재 122MB(2.4%) 사용.** 유니버스
캐시 증가율(하루 14개×약 45KB ≈ 0.6MB/일)만으로 계산해도 5GB를 채우는
데 **20년 이상** 걸린다. datacache/마커까지 더해도 자릿수가 안 바뀐다.
**결론: 볼륨 정리는 긴급하지 않다 — 우선순위를 낮춘다(사용자 결정).**

## 4. 통합 정리 정책 (설계만 — "언젠가 할 일")

긴급하지 않으므로 상세 구현은 안 하지만, 나중에 착수할 때를 위해
방향만 기록한다. 기존에 이미 채택된 패턴
(`docs/moneyflow_warmed_marker_cleanup_design.md` — 파일명에 박힌
날짜로 판정, mtime 안 씀·쓰기 시점 트리거+시작 시 보조 스윕·개별 파일
삭제 실패는 best-effort지만 로그는 남김·엄격한 정규식으로 대상 한정)를
그대로 재사용하는 방향을 제안한다 — 세 파일군 전용 정리 함수를
각자 새로 짜지 말고 공용 헬퍼 하나(`_prune_dated_files(dir, pattern,
extract_date_fn, retention_days)` 같은 형태)로 통합하면 실수(정규식
누락, 날짜 파싱 오차 등)를 한 곳에서만 관리할 수 있다.

| 파일군 | 백테스트 의존 | 제안 보존기간 | 판정 트리거(안) |
|---|---|---|---|
| `kr_universe_v6_1500_*.json` | 없음(1절에서 확인) | **당일 것만**(어제 이전 전부 삭제) | 새 슬롯 파일 저장 시 같은 날짜 이전 파일 정리 |
| `datacache_*.pkl` | 없음(측정 스크립트는 라이브 fetch만 씀, 이 캐시는 순수 서비스 성능용) | **당일 것만**(이미 `_save_disk_cache`가 이 정책으로 짜여 있음 — 로직은 그대로 두고 "정리가 실제로 도는지"를 별도 스케줄로 보강) | 기존 쓰기 시점 트리거 + **앱 시작 시 보조 스윕 추가**(2번 절의 "하루 1회도 안 걸릴 수 있음" 문제 보완) + 정리 실패를 `print()`로 가시화(현재 `except: pass`는 근본 원칙 위반) |
| `moneyflow_warmed_*.marker` | 없음 | 7일(기존 설계 문서 결론 그대로) | 기존 설계 문서(`docs/moneyflow_warmed_marker_cleanup_design.md`) 그대로 |

**절대 지우면 안 되는 것(백테스트 의존 확인됨)**: 이 세 파일군에는
해당 없음 — 단, 향후 다른 `/data` 파일을 정리 대상에 추가할 땐 매번
`scripts/` 전체에서 해당 파일명이 인용되는지부터 검색해 확인할 것
(이번 조사와 같은 방법 — README 규칙3 정신과 동일하게 "확인 없이
지우지 않는다"가 원칙).

**주의(2026-09-02 저널 사고에서 확인된 것과 무관)**: 이 세 파일군은
전부 "현재 시점만 가리키는" 인메모리 캐시 구조라 브라우저 탭이
과거 내용을 들고 있다가 되살려 쓰는 위험이 없다(CLAUDE.md "알려진
설계 갭" 참고) — 실제로 착수할 때 그 문제는 신경 쓸 필요 없음.
